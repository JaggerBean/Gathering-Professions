# Profession modules bug review — 2026-10-09

Reviewed Gathering Professions 0.29.1 and Crafting Professions 0.4.0, including their shared recipe engine, gathering integration, tools, rewards, actor state, abilities, bounties, UI, and installed dnd5e/Gatherer source.

No implementation changes or live world changes were made. This report records 20 findings: seven P1 (high priority), twelve P2 (moderate priority), and one P3 (low priority). Sixteen findings have isolated in-memory reproductions; four are supported by source tracing. These are reproducible problems found in this review, not a claim that every remaining bug has been identified.

## Original high-priority findings

### 1. Fortune-die buttons use the old dataset names

Locations: [main.js:216](E:/Foundry/FoundryVTT/Data/modules/gathering-professions/scripts/main.js:216), [gather-ui.js:411](E:/Foundry/FoundryVTT/Data/modules/gathering-professions/scripts/gather-ui.js:411).

The markup emits `data-gp-actor` and `data-gp-climb`, but both handlers read `dataset.epActor` and `dataset.epClimb`. Chat therefore cannot resolve the actor and disables the button as already rolled. The gathering window passes undefined IDs to the climb API. A natural-20 rare find can remain pending with no working normal UI control to finish it.

Evidence: source trace of both handlers and their generated markup. Repair direction: consistently use `gpActor`/`gpClimb`; verify clicks in chat and the gathering window, not only generated HTML.

### 2. Profession checks omit dnd5e exhaustion reductions and other roll rules

Locations: [main.js:436](E:/Foundry/FoundryVTT/Data/modules/gathering-professions/scripts/main.js:436), [refining.js:577](E:/Foundry/FoundryVTT/Data/modules/gathering-professions/scripts/refining.js:577), [craft.js:144](E:/Foundry/FoundryVTT/Data/modules/crafting-professions/scripts/craft.js:144), [abilities.js:126](E:/Foundry/FoundryVTT/Data/modules/crafting-professions/scripts/abilities.js:126), [askaround.js:104](E:/Foundry/FoundryVTT/Data/modules/crafting-professions/scripts/askaround.js:104).

These actions evaluate a plain `Roll` using an ability modifier or skill total. They do not run dnd5e's roll configuration, condition reductions, or advantage/disadvantage handling. In the installed 2024 rules, exhaustion subtracts two per level through `addConditionRollReduction`; that is separate from the raw ability/skill numbers. Extra gathering attempts add exhaustion, but the resulting profession checks ignore its roll penalty. Checks also bypass applicable system roll bonuses and condition disadvantage.

Evidence: source trace against installed dnd5e's `addConditionRollReduction` and `_buildSkillToolConfig`. Repair direction: use the system check pipeline with the profession die, or explicitly preserve equivalent system modifiers and condition handling in a shared check builder. Update displayed success odds as well.

### 3. Timed rewards can be delivered twice

Location: [refining.js:629](E:/Foundry/FoundryVTT/Data/modules/gathering-professions/scripts/refining.js:629).

`deliverDueJobs` snapshots due jobs before awaiting their removal. Two overlapping invocations can snapshot the same job, both remove its flag, and both award it. Removal is not an atomic claim. World-time hooks start deliveries without awaiting or serializing prior runs, so this does not require two different GM clients.

Evidence: two concurrent calls delivered two items from one queued job. Repair direction: serialize deliveries per actor and give each job an authoritative, idempotent claim/settlement process.

### 4. Failed timed delivery permanently removes the reward record

Location: [refining.js:632](E:/Foundry/FoundryVTT/Data/modules/gathering-professions/scripts/refining.js:632).

The job flag is deleted before gold or items are awarded. If an actor update or embedded-item creation fails, the job is gone and cannot retry. A bounty containing both gold and a find can also pay the gold, fail on the item, and leave no recoverable pending job.

Evidence: a simulated item-creation failure left zero items and zero queued jobs. Repair direction: retain a pending settlement record until delivery succeeds; track individual reward components so retries cannot duplicate partially delivered rewards.

### 5. Concurrent recipe actions can reuse the same ingredients and bounty eligibility

Locations: [refining.js:565](E:/Foundry/FoundryVTT/Data/modules/gathering-professions/scripts/refining.js:565), [craft.js:129](E:/Foundry/FoundryVTT/Data/modules/crafting-professions/scripts/craft.js:129), [craft.js:254](E:/Foundry/FoundryVTT/Data/modules/crafting-professions/scripts/craft.js:254), [state.js:58](E:/Foundry/FoundryVTT/Data/modules/crafting-professions/scripts/state.js:58).

The engines check inventory, completion, and limits before awaiting the roll or writes. There is no actor transaction covering the check, consumption, and award. `removeFromInventory` silently succeeds if the requested quantity is no longer present. Two overlapping actions can both pass with one recipe's materials; contact uses and one-time contract completion have the same check-before-write race. The Recipes window's visual busy state does not coordinate other clients or API callers.

Evidence: two concurrent crafts made 20 Nails from one Copper Ingot, where only 10 should be possible. Repair direction: serialize and revalidate the entire action on an authoritative client; fail consumption when inventory is insufficient.

### 6. Masterwork and perk-bearing gathering tools fail the gathering tool requirement

Locations: [craft.js:160](E:/Foundry/FoundryVTT/Data/modules/crafting-professions/scripts/craft.js:160), [nodes.js:180](E:/Foundry/FoundryVTT/Data/modules/gathering-professions/scripts/nodes.js:180).

Crafting removes `_stats` from the product snapshot, then changes the name for Masterwork/perks. Gathering accepts tools by source UUID or exact name, and does not match the retained `defaultTool` flag. A crafted `Masterwork Miner's Pick` therefore matches neither the source nor the configured `Miner's Pick` name. The default Excellent result can produce an unusable gathering tool.

Evidence: a crafted Masterwork pick retained its default-tool flag but `itemMatchesTool` returned false. Repair direction: preserve a stable product/source identity and match it across quality/name changes.

### 7. Stacking by name loses crafted-item differences and pending perk choices

Location: [refining.js:540](E:/Foundry/FoundryVTT/Data/modules/gathering-professions/scripts/refining.js:540).

`addToInventory` merges any incoming item with an existing same-name item by increasing quantity only. Its incoming flags, damage, effects, durability, and other data are discarded. Two Masterwork Daggers awaiting different GM perk choices stack under the first token; the second chat card cannot find its token. A GM then applies one perk to the whole existing stack rather than the individual item that earned it.

Evidence: two items with tokens `first` and `second` became a quantity-two item carrying only `first`. Repair direction: stack only equivalent stackable goods; keep gear and pending-perk rewards distinct.

## Moderate priority

### 8. The gathering allowance can be bypassed by simultaneous clients

Location: [gather-limits.js:29](E:/Foundry/FoundryVTT/Data/modules/gathering-professions/scripts/gather-limits.js:29).

The reservation queue is a client-local WeakMap. A player and GM controlling the same character can both read four used attempts, both reserve the fifth free attempt, and both write five. Both gathers proceed without the exhaustion confirmation or penalty the second action requires.

Evidence: two isolated module instances sharing one actor both returned true; the count remained five and exhaustion stayed zero. Repair direction: reserve attempts through a shared authoritative actor queue, including exhaustion updates.

### 9. Blank durability fields turn tools unbreakable or broken

Locations: [durability.js:23](E:/Foundry/FoundryVTT/Data/modules/gathering-professions/scripts/durability.js:23), [ui.js:488](E:/Foundry/FoundryVTT/Data/modules/gathering-professions/scripts/ui.js:488).

The editor stores blank maximum/current values as null. `whole` converts null to zero. A blank maximum therefore means unbreakable instead of the advertised world default. A blank current value with a positive maximum means broken instead of full durability. The editor's full-repair action also stores null for the value, so this affects normal repairs.

Evidence: normalizing blank fields produced `{max:null,value:null}`, which the reader interpreted as unbreakable. The same numeric coercion makes `value:null` zero when max is positive. Repair direction: treat null/blank/undefined as the documented fallback before numeric conversion.

### 10. Contact letters and wanted notices lack the promised inventory learning action

Locations: [crafting main.js:75](E:/Foundry/FoundryVTT/Data/modules/crafting-professions/scripts/main.js:75), [crafting main.js:87](E:/Foundry/FoundryVTT/Data/modules/crafting-professions/scripts/main.js:87).

The sheet-header and inventory-use hooks recognize only `scrollRecipe(item)`. Contact letters use a `contact` flag and wanted notices use a `contract` flag. Neither receives Learn Recipe nor intercepts ordinary inventory use, despite its description promising that workflow. The separate Recipes-window carried-item action still works.

Evidence: a recognized contact letter generated zero learning header controls and allowed the normal item card. Repair direction: use the generalized teaching-item check in both hooks.

### 11. Re-adding a removed profession resets its progression

Location: [state.js:108](E:/Foundry/FoundryVTT/Data/modules/crafting-professions/scripts/state.js:108).

Removal backs up the profession to `retired`, but choosing it again always creates rank 1, zero XP, the selected default path, and an empty talent list. The stated preservation behavior is not implemented on return. The backup remains available for manual recovery.

Evidence: a rank-3, 450-XP Wanderer returned as rank 1, zero XP, Standard, with no talents. Repair direction: restore the retired entry when the profession returns, or expose an explicit reset-versus-restore choice.

### 12. Cold Forge can damage a healthy tool

Location: [abilities.js:65](E:/Foundry/FoundryVTT/Data/modules/crafting-professions/scripts/abilities.js:65).

The target picker includes healthy tools, and the repair sets current durability to half the maximum without checking that the tool is broken. Choosing a full 10/10 tool changes it to 5/10. The ability describes restoring a broken item, not reducing a healthy item's durability.

Evidence: applying Cold Forge to a full tool reduced it from 10 to 5. Repair direction: restrict repair targets to eligible broken items and never lower current durability.

### 13. Item abilities consume their daily use without a valid target

Location: [abilities.js:128](E:/Foundry/FoundryVTT/Data/modules/crafting-professions/scripts/abilities.js:128).

The roll and `abilityUsed` write happen before item selection. With no eligible items, or if the successful target picker is closed, the action ends with no effect but the daily use remains spent. Selecting too many items also throws after spending the use.

Evidence: closing the successful item picker returned no effects while `abilityUsed` stayed true. Repair direction: choose and validate targets before committing the attempt; preserve the intended rule that a genuine failed check spends the use.

### 14. Duplicate bounty gear rows permit insufficient gear

Location: [contacts.js:158](E:/Foundry/FoundryVTT/Data/modules/crafting-professions/scripts/contacts.js:158).

The GM validator accepts the same Item name more than once. `maxBatch` tests each row against the same inventory count instead of summing them. A bounty requiring Manacles once and Manacles twice passes with only two Manacles; later removal silently tolerates the missing third item.

Evidence: the duplicate-gear body validated, required three total, and returned maxBatch 1 with inventory two. Repair direction: reject duplicate gear names or combine their requirements and consumption modes before validation.

### 15. A replacement active GM lacks essential gathering hooks

Location: [main.js:1052](E:/Foundry/FoundryVTT/Data/modules/gathering-professions/scripts/main.js:1052).

`registerNodeHooks` exits on every client except the active GM at startup. If that GM disconnects, a second already-connected GM becomes active without the actor-request, visibility, timer, or timed-delivery hooks. Existing players can receive Fortune-die timeouts; jobs and node resets stop updating until the replacement GM reloads.

Evidence: source trace of startup registration and the early return; there is no registration on active-GM handover. Repair direction: register handlers on every GM client and check authority at event time; process pending work when authority changes.

### 16. Bounty search cannot find contract titles or targets

Location: [recipes-ui.js:70](E:/Foundry/FoundryVTT/Data/modules/gathering-professions/scripts/recipes-ui.js:70).

Search matches group names and ingredient names only. Contract groups are town names; contract titles such as Garrick the Fence are stored on the rows. Searching the target's name removes the group even when that contract exists.

Evidence: Garrick appeared without a filter but searching `Garrick` returned zero groups. Repair direction: include row titles, output names, brief/target fields, and appropriate contact text in search matching.

### 17. The public Hunt API bypasses normal actor and job gates

Location: [craft.js:254](E:/Foundry/FoundryVTT/Data/modules/crafting-professions/scripts/craft.js:254).

The published `api.bounties.hunt` calls `hunt` directly. Unlike `craft`, it does not validate ownership, learned status, profession, rank, tool/gear eligibility beyond maxBatch, or the contact's remaining uses. It also accepts a caller-provided row instead of resolving a registered job. Macros or integrations can accidentally award bounty rewards to an unqualified character or bypass the contact limit. Foundry's underlying permissions do not enforce the module's profession rules.

Evidence: an owned character with no Bounty Hunter profession and no learned contract received a contract's gold through direct `hunt`. Repair direction: route the public API through the same guarded action entry point and resolve work by ID.

### 18. Nodes first gathered at world time zero do not auto-reset

Location: [nodes.js:395](E:/Foundry/FoundryVTT/Data/modules/gathering-professions/scripts/nodes.js:395).

The reset code treats `firstDrawTime === 0` as missing. Zero is also a valid first-draw timestamp at the start of a world. A depleted node with a one-hour reset remains depleted even after two hours; the window also describes it as waiting for the first pull.

Evidence: a one-pull, one-hour node used at time zero returned zero resets at world time 7200. Repair direction: use draw usage and explicit missing-value checks, rather than timestamp truthiness.

### 19. A conservation refund can restore other characters' pulls

Location: [main.js:553](E:/Foundry/FoundryVTT/Data/modules/gathering-professions/scripts/main.js:553).

The refund overwrites `drawsUsed` with the old client snapshot `before`, rather than reversing one identified pull. If another gather occurs before the GM processes the refund, its pull is restored as well. The request also trusts a caller-provided snapshot, so the GM cannot establish which specific pull it is refunding.

Evidence: executing the actual handler with `before:1` and current usage three reset usage to one; refunding a single action should leave two. Repair direction: identify, authenticate, and refund one committed draw in the same authoritative node transaction.

## Low priority

### 20. The alive reward multiplier setting has no effect

Locations: [gm.js:57](E:/Foundry/FoundryVTT/Data/modules/crafting-professions/scripts/gm.js:57), [contacts.js:287](E:/Foundry/FoundryVTT/Data/modules/crafting-professions/scripts/contacts.js:287).

The hub exposes `aliveRewardFactor` as the fallback when no alive reward is set. Runtime reward rows never read it; generated either-type contracts use a hard-coded factor, and the validator requires explicit gold for each offered choice. There is no supported path where the advertised fallback can apply.

Evidence: reference search found reads only in rule normalization, saving, and UI; no reward calculation uses the setting. Repair direction: implement a documented optional-alive-reward fallback, or remove the ineffective setting.
